# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AI 汽车运营官: an AI operations employee for car dealers who run 5 or more Xiaohongshu (小红书, "XHS") accounts. It does two jobs: **lead acquisition** (find people shopping for a car in public notes and comments, then assign, reach out, qualify and book appointments) and **content operations** (plan, write, review and publish notes for each account). It uses no runtime npm dependencies. Node ≥ 24 runs the TypeScript directly (type stripping), and `node:sqlite` is the database.

`ARCHITECTURE.md` is the **binding module contract**: signatures, scoring calibration, guard pipeline, capability truth table and the §10 production contract. Read the relevant section before changing a module's public API. A breaking change must update ARCHITECTURE.md and every caller. The UI is the 驭客 Steer design: `docs/design/steer-ui-kit.html` is the visual source of truth for the brand (mark, palette, gold-for-AI rule) and `docs/UI_DESIGN.md` records how it is applied. The console is a dense internal tool, so its layer obeys a product-UI system, not the kit's marketing layout: **one type scale** (`--st-fs-micro|meta|body|item|head|page|metric`, nothing between the steps), **three radii** (`--st-r-control` 6px for buttons/inputs/tags, `--st-r-surface` 10px for cards/tables/media, `--st-r-pill` for a status badge and nothing else), **two control heights** (`--st-ctl` 32px, `--st-ctl-sm` 26px), a labelled grouped sidebar that collapses to icons (cookie `st_rail`), gold only for AI/key state, and light + dark via cookie `st_theme`. Never introduce a fourth radius or a font-size literal. **The card is not the default container**: a bordered surface is reserved for an object that is genuinely a card (a vehicle with a photo, a note with a cover, an account with an avatar) and for a form. Everything else — tables, metric strips, funnels, to-do lists, activity feeds, detail panels — sits on the page and is grouped by a heading rule, hairlines between rows and space, because a page of identical white boxes is the single clearest sign of generated UI. Hierarchy comes from type size, weight and the ratio of between-section to within-section space. Never port the kit's sample data or animated sample feeds into the product. `docs/design/ui-reference.png` is retired. Asset URLs carry a content hash (`ASSET_VERSION`), so CSS/JS changes are never served stale; the console process still needs a restart (or `node --watch`) to pick them up.

## Commands

```bash
npm run typecheck                      # tsc --noEmit (no emit; nothing is compiled)
npm test                               # unit + integration + e2e
npm run test:unit | test:integration | test:e2e
node --test test/unit/crm/funnel.test.ts          # single test file
node --test --test-name-pattern="<regex>" test/unit/x/y.test.ts
npm run build                          # typecheck + unit tests + `doctor --build-check`
node src/cli.ts doctor [--offline] [--json]       # reports config/DB/provider/login/LLM status
npm run migrate                        # apply DB migrations to DATABASE_PATH
npm run dev                            # console with --watch (APP_ENV=development)
npm run demo                           # simulation provider + fictional demo dealer in ./data/demo.db
npm start                              # APP_ENV=production serve (scheduler runs in-process unless SCHEDULER_ENABLED=false)
npm run scheduler                      # scheduler-only worker process, no HTTP
```

There is no linter; `typecheck` + tests are the gate. Config is env-only (`src/app/config.ts`, template in `.env.example`); load it with `set -a && . ./.env && set +a`. `dist/` only holds the built macOS `.app` bundles.

Live XHS test (`npm test`'s glob includes it, but it skips itself unless this env var is set): `XHS_LIVE_MCP_URL=http://127.0.0.1:18060/mcp XHS_LIVE_MCP_TOKEN_FILE=… node --test test/live/xhs-live.test.ts`.
Run one xiaohongshu-mcp instance for each account: `scripts/xhs-mcp-fleet.sh start|status|stop` (with `XHS_MCP_BIN` + `XHS_MCP_DATA_DIR` + `XHS_MCP_TOKEN` set, the console starts a new account's instance itself: 账号 → 启动本机实例); log one in with `scripts/xhs-mcp-fleet.sh login <research|platform_account_id>` (build the Go helper `tools/xhs-visible-login` once with `XHS_MCP_SRC=… scripts/xhs-mcp-fleet.sh build-login-helper`). The macOS app is built with `scripts/macos/build-app.sh`. Server deploy without Docker (Ubuntu + systemd): `scripts/deploy.sh setup|release <ssh-host>`, `tls <ssh-host> <ip>` and `domain <ssh-host> <domain> <email>` (`docs/DEPLOYMENT.md` §3a/§3b/§3c; nginx/systemd units live in `deploy/`). Docker Compose is the alternative (§4). `desktop/` is a separate Electron package (its own devDependencies, not part of the server runtime): a window onto the cloud console that pins the server certificate fingerprint from `desktop/server.json`.
Other CLI subcommands (`dealer import/export`, `goal`, `run <workflow>`, `xhs-login`, `import-content`) are listed in the header of `src/cli.ts`.

## Code conventions (enforced by tsconfig / contract)

- **Erasable syntax only**: no `enum`, `namespace`, constructor parameter properties or decorators. Use `as const` arrays with union types instead.
- Relative imports **must include the `.ts` extension**. Type-only imports use `import type`.
- Every skill and operator function takes `ctx: AppContext` first (`src/app/context.ts`: `db, clock, audit, xhs, llm, skills, log, runId`). There are no globals.
- Time: always use `ctx.clock.now()` / `ctx.clock.iso()`, never `new Date()` / `Date.now()` in business logic. Dealer-local days come from `src/core/time.ts` using `dealer.settings.timezone`.
- `ctx.db.tx(() => …)` is **synchronous only**. Never `await` inside it. Call providers and the LLM first, then persist inside the transaction.
- IDs come from `newId(prefix)` with the fixed prefix list in ARCHITECTURE §1. Inputs are validated with `src/core/validate.ts`. Errors use `NotFoundError` / `ValidationError` / `PolicyError(code, msg)`.
- AI decisions are recorded with `ctx.audit.decision(...)` and state changes with `ctx.audit.event(...)`.
- DB entities are snake_case and map 1:1 to columns. JSON and boolean columns are converted using `TABLE_META` in `src/db/schema.ts`. Schema changes are new entries appended to `MIGRATIONS` (currently v1–v12). Never edit an existing migration.
- Customer-facing generated text is Simplified Chinese. The UI is Chinese-first. Code and comments are English.
- Tests use `node:test` + `node:assert/strict` with `createTestContext()` from `test/helpers/context.ts`. It gives an in-memory migrated DB, a `ManualClock` fixed at `2026-09-12T02:00:00Z` (Saturday 10:00 Shanghai), and **unavailable** XHS/LLM providers unless you pass them in. Use `test/helpers/fixtures.ts` for setup: `loadDealerFixture(ctx)`, `dealerIdByKey`/`accountIdByPlatformId`, and `seedLead`/`seedOutreach`/`seedAppointment`/… for rows in a given state. The fixture keys tests refer to (`hz-bmw`, `xhs-hz-official`, corpus users like `u-hz-buyer-001`) are defined in ARCHITECTURE §9. The simulation corpus is `fixtures/xhs/simulation-corpus.json`.

## Architecture

**Layers:** `src/core` (types, ids, clock, validate, errors) → `src/db` + `src/audit` → `src/providers/{xhs,llm}` → `src/domain` (automotive lexicon, dealer profile, pure actor classification) → `src/skills` → `src/operator` → `src/server` + `src/cli.ts`. `src/app/bootstrap.ts` `createRuntime(config)` migrates the DB, recovers interrupted runs, registers skills and workflows, and ensures schedules.

**Skills** live at `src/skills/<category>/<name>/index.ts`, grouped into the categories research, content, acquisition, sales and operations. Each one exports plain typed functions for direct use **and** `export const skill = defineSkill({name, category, agent, input, run})` so the Operator can invoke it by name. Each skill directory has a `SKILL.md`. Every skill must be registered in `src/skills/index.ts`: `test/unit/operator/workflows.test.ts` checks that every skill directory on disk is registered.

**Operator** (`src/operator`): goal-parser → planner → `workflows.ts` (named daily workflows such as `lead_discovery`, `reply_processing`, `content_publishing`, `evening_analysis`) run by a resumable `workflow-engine.ts`. `scheduler.ts` triggers them in the dealer's timezone. `onboarding.ts` `requireReadyToRun` refuses goals and manual runs until the dealer has at least one active account whose QR login was verified by a live probe. Only `refresh_dealer_data` is exempt.

**车型库 / Vehicle Brain** (`src/skills/operations/vehicle-brain`, ARCHITECTURE §8 A1): the store's in-sale line-up as **cards** — the `vehicles` row (photos, 指导价, 当前售价, specs, 卖点, 适合人群, 竞品, FAQ, 选题角度) plus that dealer's live `inventory` colours/stock and the `offers` that apply to it, with `fact_refs` for every number. It is the single retrieval layer for facts about cars: `retrieveVehicles` / `matchVehicle` (deterministic lexical matching — model/alias/trim first, then the query's discriminating character bigrams, those some but not all cards have; no vector store) and `vehicleContext` (a labelled 事实 / 素材 block for prompts). Content, outreach, conversation and the lead pipeline all read it, so an **archived** trim leaves the line-up everywhere at once (`findVehicles` / `resolveVehicle` exclude archived by default). `knowledge.ts` generates the prose with an LLM and drops every string that fails either guard — `verifyClaims` and `unsupportedMeasurements` (each 数字+单位 must exist on the card; 万↔元 and 成↔% resolved; the model year exempt) — so a price, a spec or a stock claim can never be invented. Console: 车型 page (`/vehicles`, cards + 批量导入 CSV/JSON + AI 生成资料 + 归档), 设置 → 在售车型 links there.

**账号语言风格 / Account Voice** (`src/skills/content/account-voice`, ARCHITECTURE §8 A1): each managed account keeps writing the way it already writes. `learnAccountVoice` reads that account's **own** published notes (profile list → detail per note, notes this system published are skipped so a voice never learns from itself), measures them in `analyze.ts` (title length, sentence rhythm, paragraphs, emoji density and which emoji, punctuation, 你/您, first person, spec quoting, model naming, CTA, tags, recurring phrases) and turns the measurements into executable rules, each with the measurement that produced it, plus 2–3 of its own notes as few-shot examples. One row per account (`account_voice_profiles.account_id` UNIQUE) — profiles are never shared or merged. Everything is median/share based with a support threshold (`RULE_SUPPORT` 0.4), so one odd post cannot move a voice; below `MIN_SAMPLES` (3) usable notes nothing is stored. LLM-added rules must quote a verbatim passage from that account's notes and may not contain a price or spec number. `voicePromptBlock` goes into note generation and DM polishing, `applyVoicePronoun` into conversation replies, and **`voiceCopyCheck` rejects any output that reprints one of the account's own notes** (similarity ≥ 0.55 or ≥ 18 characters of verbatim overlap). Refreshed weekly by the `learn_account_voice` step of `refresh_dealer_data`, or from the 账号 card.

**Lead pipeline** (ARCHITECTURE §3, §5, §10): leads belong to the **store**, never to an account — removing an account releases its leads back to the dealer pool (and archives the account when it has customer history) and the hourly `assign_leads` step re-owns them. Query generation → provider search → notes and comments stored with `data_mode` provenance → prefilter → intent detection → `classifyActor` (only `BUYER` signals create leads) → scoring → `upsertLeadFromSignal` (one lead per person per group; writes provenance for every signal path) → Fleet Controller assigns exactly one owning account → outreach through the **10 ordered pre-send guards** (§6). CRM stage rules are in §4 (`WON` only from `CONTACTED` or later; `LOST` is left only via `reopenLead`). The scoring rules in §5.1–5.3 (author roles, owners are not buyers, out-of-area cap, group matching) fix the defects F1–F5 recorded in `docs/PREVIEW_FINDINGS.md`. `test/integration/scoring-calibration.test.ts` enforces the §5 reference table, so any change to NLU or scoring must keep it passing.

**XHS provider** (`src/providers/xhs`): `mcp` is live (one xiaohongshu-mcp instance/login session per managed account plus a research instance, configured by `XHS_MCP_ACCOUNTS` or `xhs_accounts.mcp_endpoint_url`), `simulation` is a labelled synthetic corpus, and `none` is unavailable. Truths the code depends on (§7):
- There is **no authorized DM API** a store can call: the official IM API is open only to approved third-party 客服服务商, 聚光 covers ads/reports/客资 only, and the 专业号 workbench needs its own login. Receiving DMs is therefore impossible. Sending is possible only through the account's own logged-in session (`tools/xhs-dm-send`, opt-in per deployment via `XHS_DM_SENDER` + `XHS_MCP_DATA_DIR`, loopback instances only); with it off — the default — outreach ends at review, a human sends it and records `SENT_MANUALLY` + `sent_by`. `SENT` always requires a provider-confirmed message id (here: the message read back in the conversation). An unknown outcome is `REQUIRES_REVIEW`, never retried and never auto-sent again.
- A logged-out session surfaces as `REQUIRES_AUTH`, never as "no results". There is no silent fallback from `mcp` to simulation. Login checks are never cached. 账号 → 退出登录 (`delete_cookies`) clears an instance's session and leaves the account `requires_auth`.
- Xiaohongshu rejects QR logins scanned from the instance's headless browser (`get_login_qrcode`). Login goes through a visible window (`tools/xhs-visible-login`, console 登录窗口 via `XHS_LOGIN_HELPER` + `XHS_MCP_DATA_DIR`, loopback instances only) that writes the instance's `cookies.json`.
- Tool calls are queued per instance (each one launches a browser); never add a code path that calls `ep.client.callTool` directly instead of the provider's `callTool`.
- Publishing needs at least 1 image and returns no note id. A post with a `video` (one absolute path on the instance's host) is published as a **video note** through `publish_with_video` instead, with no images. Unknown outcomes are never auto-retried.
- The platform's **notification centre** (`list_notifications` / `get_unread_count`) is readable: 评论和@, 赞和收藏, 新增关注. Reading a tab clears its unread badge, so the counts are read first; `filtered` (entries the platform hid) is always carried through. `notification-inbox` stores them in `xhs_notifications`, buyer comments become leads through the normal pipeline, and the 对话 page shows the three tabs beside 私信. A like, a collect or a follower is never a lead by itself.
- 聚光 lead pushes arrive through `/webhooks/juguang` (`juguang-webhook.ts`).
- If an instance's `tools/list` shows a DM-like tool, both message capabilities become `REQUIRES_REVIEW`, never `AVAILABLE`. `src/providers/xhs/README.md` has the full live-detection rules.

**LLM** (`src/providers/llm`: OpenRouter or Anthropic, chosen by `LLM_PROVIDER` / whichever key is set) is optional. Four call sites use it: intent refinement (`completeJson`), **lead screening** in discovery (`completeJson`, `lead-discovery/llm-screen.ts`: with an LLM configured only screened buyers become leads; a failed call leaves candidates unscreened, never a rules fallback; live eval `LIVE_LLM_EVAL=1 node --test test/live/lead-screen-live.test.ts` on hand-labelled real comments must keep precision ≥ 0.85 / recall ≥ 0.8), DM polishing (`completeText`) and note generation (`completeJson`); JSON schemas go through `toStructuredOutputSchema` (no `enum` next to a union `type`: it is rewritten to `anyOf`). The deterministic engines must be complete without it, and LLM output is always validated: quotes must be verbatim substrings, and claims are checked against the Dealer Brain with `verifyClaims`. Dealer facts (prices, stock, offers) come only from the imported Dealer Brain.

**Server** (`src/server`): hand-rolled router (`http.ts`), JSON API in `api/`, server-rendered pages in `pages/`, cookie session auth (required in production), CSRF via `x-console-request: 1` or same-origin fetch metadata, `/healthz` and `/readyz`. An anonymous visitor of `/` gets the **public site** instead of a login redirect (`pages/landing.ts` + `site-css.ts`, also at `/welcome`): edge-to-edge layout with 3D pieces (the brand kit's flow in SMIL, a screenshot that stands up on a CSS scroll timeline, the mark as a stacked solid); its only script (`SITE_JS`, `/assets/site.js`) feeds pointer position to them and nothing depends on it; no external resources, no drawn mock-ups and no invented numbers. The product is shown with real console screenshots of the one store that agreed to be named (舟山小鹏), taken with every Xiaohongshu user's name, avatar and words blurred, served only from the whitelist in `site-images.ts` (`/assets/site/:name`); the case figures in `CASE` carry the dates they were read on. Its 预约演示 form posts to `/demo-request` (rate-limited, validated, stored in `demo_requests`) and the requests are handled on 系统 → 官网预约; 客户登录 goes to `/login`.

## Hard rules for this project

- **Never assume a dealer, brand, city, model or account.** Nothing in `src/` may hard-code one. Each store enters its own data in the console (设置 / 账号) and logs its own XHS accounts in by QR code. `fixtures/dealers/hangzhou-bmw-group.json` is a fictional bundle **for tests and the dev demo only**. Never import it into a non-test database, and never use BMW or other placeholder defaults in the UI.
- `APP_ENV=production` refuses the simulation provider and `seed-demo`, and requires `CONSOLE_PASSWORD`, `SESSION_SECRET` and a persistent `DATABASE_PATH`. Keep these refusals.
- Unfinished features are never presented as working: they are registered in `src/server/unfinished.ts`, but the page helpers (`unfinishedTag`/`unfinishedButton`/`unfinishedBlock`) render **nothing** — the disclosure lives in one place, 系统 → 还没做完的功能. When you implement one, delete its registry entry and its helper call in the same change.
- The console speaks the store's language. Tool names, instance ids, endpoints, env names, English status codes, ids, skill/agent names and raw provider errors must never reach a page: run user-facing text through `src/server/humanize.ts` (`scrubInternals`, `humanProblem`, `humanActor`, `humanAction`, `humanCapability`, …). `test/unit/server/no-internals.test.ts` renders every page with live-shaped data and fails on a leak.
- Explanations live behind a 「?」, not on the page: `hint(text | text[])` (`src/server/render.ts`, re-exported from `src/server/hint.ts`), `sectionHead(title, { help })` and `renderPage({ help })` for the page's own title. A page shows one sentence of conclusion; the rest is one click away. A page subtitle is the store's name plus at most one short changing fact — what the page is for belongs in its `help`, never in the subtitle or a lede paragraph.
- **Never show system internals in the console.** Tool names (`xiaohongshu-mcp`, `search_feeds`…), instance URLs and ports, env var names, English status codes (`UNAVAILABLE`, `REQUIRES_AUTH`), internal agent / skill names, and our own row ids are diagnostics: they belong in the audit log and the server log. `src/server/humanize.ts` is the only place that turns them into store language (`humanProblem`, `humanCapability`, `humanAgent`, `humanActor`, `humanAction`, `humanSubject`, `humanEngine`, `scrubInternals`), and operator-facing `PolicyError` messages are written the same way — say what to click, not which process to start. `test/unit/server/no-internals.test.ts` renders every page with a live provider and realistically ugly data and fails if any of it leaks into visible text or a tooltip.
- Unverified state is never shown as fact. For example, an account shows 登录未检测 until a live probe sets `auth_checked_at`.
